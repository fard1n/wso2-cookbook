Architecture Official WSO2 4.7

1. The 4-Portal Architecture & The Gateway

WSO2 API Manager 4.7 decouples its platform into 4 specialized web portals plus a headless runtime engine.

Instead of a single monolithic user interface, WSO2 separates responsibilities based on enterprise security boundaries, persona roles, and runtime isolation. Understanding who uses which interface is the key to mastering the platform:

🎨 Publisher

/publisher

For API Creators & Product Owners. Design APIs, define OpenAPI specs, configure backends, attach policies, and manage revisions & lifecycle.

🛍️ Devportal

/devportal

For API Consumers & Developers. Self-service marketplace. Discover published APIs, create client Applications, subscribe, generate OAuth2 tokens, and test.

⚖️ Admin Portal

/admin

For Operations & Platform Governance. Define rate limiting tiers, configure third-party Key Managers (Okta, Keycloak), blacklist IPs, and approve workflows.

⚙️ Carbon Console

/carbon

For Core Infrastructure Engineers. Legacy administration interface for direct LDAP/AD user stores, registry, and low-level Identity Server OAuth service providers.

⚠️ The Gateway Has NO Portal!

The Gateway (e.g. https://api.parspc.ir on port 8243) is the high-performance runtime proxy. It has no web UI. Opening it in a browser returns an HTTP 404 JSON response. It only processes automated HTTP API requests bearing an Authorization: Bearer <token> header.

2. Publisher Portal (`/publisher`)

The creative and lifecycle management hub for designing and publishing digital APIs.

Primary Capabilities

  • API Design & Prototyping: Visual editing of OpenAPI 3.0 specs, schemas, and mock responses.
  • Security & Policy Attachment: Attaching CORS, header transformations, schema validation, and OAuth scopes.
  • Backend Endpoint Composition: Routing requests to HTTP REST, SOAP, AWS Lambda, Load Balanced, or Failover endpoints.
  • Revision Deployment: Creating immutable snapshot revisions and promoting them across Gateway environments.
  • Lifecycle Governance: Transitioning APIs through formal states (Created, Prototyped, Published, Deprecated, Retired).

3. Official API Creation Wizards

WSO2 APIM 4.7 provides 6 distinct creation modalities depending on your backend protocol.

1. Design a New REST API

When to use: You are starting from a blank slate or want to manually define paths, parameters, and endpoints inside APIM's visual editor.

Required Fields: Name, Context (e.g., /billing), Version (e.g., 1.0.0), Endpoint (target backend address), and Business Plan.

2. Import OpenAPI / Swagger

When to use: You already have a standard OpenAPI 2.0 / 3.0 spec (JSON or YAML) from Swagger, FastAPI, Spring Boot, or Postman.

Modes: Upload file or provide a public URL. APIM automatically generates all resources, data types, parameter validations, and documentation from the spec.

3. Import SOAP / WSDL

When to use: Legacy enterprise backend integration. APIM gives two powerful modes:

  • Pass-through: APIM proxies raw SOAP XML envelopes over HTTP/HTTPS, adding rate limiting and OAuth2 security.
  • Generate REST API (SOAP to REST): APIM parses the WSDL operations and automatically generates RESTful JSON endpoints. Incoming JSON requests are converted to SOAP XML on the fly and sent to the legacy service, and XML responses are translated back to JSON!

4. GraphQL API

When to use: Modern GraphQL backend. Upload your .graphql schema definition.

Special Features: Field-level authorization, query complexity analysis, and query depth limiting to prevent malicious recursive queries from overloading your backend.

5. Async / Streaming APIs

When to use: Event-driven architecture. Supports:

  • WebSocket: Full-duplex persistent connections.
  • WebSub / Webhooks: Event notification topics where consumers register callback URLs.
  • Server-Sent Events (SSE): Unidirectional event streaming from backend to client.

6. Create API from Service Catalog

When to use: Micro Integrator (MI) integration. MI pushes its deployed services via HTTPS into the catalog. Click Create API to immediately wrap the integration service with API management policies.

4. Deep Dive: Inside the API Studio

A complete tour of the left sidebar menus when configuring an individual API.

Left MenuWhat It Controls in WSO2 APIM
Overview Dashboard showing active lifecycle status (CREATED, PUBLISHED), rating, public gateway URLs, tags, and quick actions.
API Definition The embedded Swagger / OpenAPI 3.0 Editor. Edit raw YAML/JSON or use visual forms to add request body schemas, header definitions, and response codes.
Endpoints Defines where traffic is forwarded:
• HTTP/REST Endpoint: Standard single backend URL.
• Load-Balanced Endpoints: Multiple server URLs with Round Robin or Weighting.
• Failover Endpoints: Primary server with automated failover to secondary servers on timeout.
• AWS Lambda Endpoint: Direct invocation of serverless functions using AWS credentials.
• Endpoint Security: Basic Auth, Digest Auth, or OAuth 2.0 Client Credentials flow to the backend.
Resources HTTP operations tree (GET, POST, PUT, DELETE, PATCH):
• Operation Security: Toggle OAuth on/off per resource.
• Resource Throttling: Apply specific rate limits to heavy resources (e.g. 5 req/min on POST /transfer).
• OAuth Scopes: Restrict resources to specific scopes (e.g. admin:write).
Policies (Mediation) The Policy Hub: Drag-and-drop mediation pipeline. Three sequential execution flows:
1. Request Flow: Add/remove headers, path rewriting, payload schema validation.
2. Response Flow: Modify backend response headers, sanitize JSON data, CORS injection.
3. Fault Flow: Custom error mapping when backend fails or times out.
Runtime Configurations Transport selection (HTTP/HTTPS), MTOM for binary attachments, and Response Caching (TTL in seconds).
Subscriptions Select available Business Plans / Tiers (Unlimited, Gold, Silver). Mandatory: You cannot publish an API without at least one plan selected.
Deployments Revision Management: APIM does not push live draft changes directly to the gateway.
1. You create an immutable Revision (e.g. Revision 1).
2. You deploy that revision to target Gateway environments.
Lifecycle The official state machine:
• CREATED: Draft. Gateway returns 404.
• PROTOTYPED: Mock testing.
• PUBLISHED: Live in Devportal. Gateway executes calls.
• BLOCKED: Temporarily suspended. Gateway returns 503.
• DEPRECATED: Sunset notice. Existing subscribers still work.
• RETIRED: Permanently decommissioned.
Documents Documentation engine. Attach Markdown pages, PDF files, URLs, or inline help text for API consumers.

5. Developer Portal (`/devportal`)

The self-service API marketplace where application developers discover, subscribe, and obtain credentials.

Core Concepts

Devportal treats APIs as products in an online store. Consumers do not just call an API; they enter into a governed relationship with rate limits and credentials.

Key Developer Portal Features

  • API Catalog & Smart Search: Search by tag, API name, context, documentation content, or provider.
  • Interactive Swagger Console: Test endpoints directly inside the browser.
  • Client SDK Generation: One-click export of ready-to-run client code in Java, Python, JavaScript, C#, PHP, Go, Ruby, and Android.
  • Community & Ratings: Five-star rating system, consumer feedback, and technical comments per API.

6. Applications, Subscriptions & Key Generation

Why WSO2 uses "Applications" instead of user-level keys, and how token generation works.

Why Does the "Application" Concept Exist?

In simple platforms, an API key is tied to a user account. In WSO2, client credentials belong to an Application. This architecture solves three critical enterprise problems:

  1. Multi-API Bundling: One client application (e.g. MobileBanking-App) can subscribe to 10 different APIs (Account API, Transfer API, Loans API) and invoke all of them using a single OAuth2 token!
  2. Environment Isolation: An Application has separate Production Keys and Sandbox Keys. You can test in sandbox without risking production rate limits or data.
  3. Application Throttling: Protects the backend from consumer bugs. If one buggy mobile app loops endlessly, the Application rate limit cuts it off without affecting other applications.

Generating OAuth2 Keys in Devportal

Inside Applications → [Your App] → Production Keys:

  1. Click Generate Keys. APIM assigns:
    • Consumer Key (Client ID): The public identifier for your app.
    • Consumer Secret: The private secret key used to authenticate.
  2. Select Grant Types supported by your application:
    • Client Credentials: Machine-to-machine background services.
    • Authorization Code: Web applications with user redirection (PKCE supported).
    • Password: Legacy direct username/password authentication.
    • Refresh Token: Refreshing expired access tokens without re-authenticating.
  3. Click Generate Token: APIM issues a signed JWT Bearer token: 
    eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhZG1pbiIs...

7. The API Console (Try Out Screen Demystified)

Understanding the Try Out interface and why anonymous viewing causes confusion.

🚨 The "Anonymous View" Trap

When you open Devportal without logging in (it displays the SIGN-IN button in the top right):

  • Devportal allows you to browse public APIs.
  • However, when you open the API Console (Try Out), Devportal cannot generate an OAuth token for you because anonymous guests have no Application or Subscriptions!
  • Instead of showing a warning, it silently switches Security Type to Basic and prompts for a manual Username/Password.
  • Fix: Always click SIGN-IN first! Once logged in, the Security Type switches to OAuth, lists your Applications, and auto-generates test tokens with one click.

How to Test Inside the API Console (Logged In)

  1. Select Security Type: OAuth.
  2. Select your subscribed Application from the dropdown.
  3. Select key type: Production.
  4. Click Get Test Token (injected automatically into the swagger header).
  5. Expand any resource (e.g. GET /phones), click Try it out, and click Execute.

9. The Multi-Tier Throttling Engine

WSO2 APIM features one of the most granular rate-limiting engines in the industry, evaluated at four distinct tiers.

1. Subscription Policies (Commercial Plans)

Enforced per consumer subscription to an API. Defines commercial tiers like:

  • Unlimited: No request caps.
  • Gold: 5,000 requests per minute with burst limit of 200 req/sec.
  • Silver: 500 requests per minute.
  • Bronze: 50 requests per minute.

2. Application Policies (Client Defense)

Enforces a hard ceiling on the total requests an application can emit across all APIs combined. Protects internal infrastructure from buggy consumer client loops.

3. Advanced Throttling (Dynamic Conditions)

Define rules evaluated on runtime request attributes:

  • IP / IP Range: Limit a specific partner IP subnet to 10 req/min.
  • HTTP Header: Throttle based on custom headers (e.g. X-Customer-Tier: Free).
  • JWT Claims: Read claims inside the token (e.g. department == "sales") and apply rate rules.

4. Blacklisting (Deny Policies)

Instantly block rogue traffic at the Gateway edge: Block by IP address, IP subnet range, Application name, User ID, or API context.

10. Carbon Management Console (`/carbon`)

The low-level OSGi runtime administration interface underneath the WSO2 suite.

The Carbon Console is the legacy underlying engine that powered earlier generations of WSO2 products. In modern APIM 4.x, almost all day-to-day functions have been migrated to the modern React-based Publisher, Devportal, and Admin portals.

When Do You Still Use Carbon in APIM 4.7?

  • User Store Management: Configuring secondary LDAP or Active Directory user stores.
  • Registry Browser: Browsing low-level WSO2 Governance and Config registries.
  • Service Providers: Configuring underlying SAML/OIDC Single Sign-On (SSO) service providers for the portals themselves.
🚨 The Carbon Golden Rule

Do not create or edit APIs in Carbon! Carbon is not an API catalog. Modifying API artifacts directly in the Carbon registry will desynchronize the API Manager database and break Publisher revisions.

11. The Gateway Runtime (Headless Engine)

How traffic executes through the Gateway at runtime without human intervention.

The Gateway is the only component that clients and mobile apps talk to in production. Here is its step-by-step millisecond execution pipeline:

[Client Request]
       │
       ▼
1. TLS Handshake & Host Routing (api.parspc.ir :8243)
       │
       ▼
2. Path Matching (Context + Version: /phonebook/1.0.0/phones)
   └─► If API is in CREATED state or path is wrong: Returns 404 NOT FOUND
       │
       ▼
3. Security Validation
   ├─► Checks "Authorization: Bearer <JWT>"
   ├─► Verifies digital signature with public certificate
   ├─► Checks token expiration and OAuth scopes
   └─► Missing or expired: Returns 401 UNAUTHORIZED
       │
       ▼
4. Rate Limiting (Throttling) Evaluation
   ├─► Checks Subscription tier quota (e.g. Unlimited)
   ├─► Checks Application tier quota
   ├─► Checks Blacklist & IP rules
   └─► Limit exceeded: Returns 429 TOO MANY REQUESTS
       │
       ▼
5. Policy Execution (Request Flow)
   └─► Injects headers, applies CORS, transforms JSON
       │
       ▼
6. Backend Forwarding
   └─► Calls Backend Endpoint Base + Resource Path
       │
       ▼
7. Response Processing & Return
   └─► Injects response headers, checks cache, returns 200 OK to Client
