Module 1 of 12 Overview

1. The Practitioner's Mental Model

Understand the core division of labor between WSO2 Micro Integrator (building integration logic) and API Manager (governing APIs).

The Two Engines & Who Does What

When working with WSO2, the foundational mental model is understanding that Micro Integrator (MI) and API Manager (APIM) serve two fundamentally distinct purposes:

CapabilityWSO2 Micro Integrator (MI 4.5)WSO2 API Manager (APIM 4.7)
RoleIntegration Engine / ESBAPI Management & Gateway
Primary JobData transformation, orchestration, calling databases, EIP.Security (OAuth2/JWT), rate limiting, lifecycle, analytics.
InterfaceVS Code Extension / Integration Studio (.car files)Web Portals (Publisher, Devportal, Admin)
ConsumerCalled internally by APIM or backend systems.Invoked directly by external apps, clients, and partners.
Ports8290 (HTTP), 8253 (HTTPS)8243 (Gateway), 9443 (Portals/Management)

Kind A vs. Kind B APIs

Every API in your organization falls into one of two implementation patterns:

1. Kind A: Direct HTTP Proxy (Publisher Only)

Your backend is already a modern REST API that speaks JSON over HTTP. You do not need MI here. You go straight to Publisher → Create API → Import OpenAPI, enter the backend URL, configure rate limits, and publish.

2. Kind B: Integration / Data Service (MI + APIM)

Your backend is a database table (SQL Server, PostgreSQL), a legacy SOAP service, or requires calling multiple APIs and merging their JSON responses. You build this in MI first, deploy it as a Data Service (.dbs) or Integration API, push it to APIM via Service Catalog, and then govern it in Publisher.

The Portals Landscape

  • Publisher (/publisher): For API developers. Design APIs, set endpoint URLs, attach policies, manage lifecycle.
  • Devportal (/devportal): For API consumers. Browse published APIs, create applications, generate OAuth2 keys and Bearer tokens.
  • Admin (/admin): For platform administrators. Configure Rate Limiting tiers (Gold, Silver, Unlimited) and Key Managers.
  • Gateway (https://api.parspc.ir): The traffic runtime engine. Has no login UI. Accepts client requests with Bearer tokens.
Module 2 of 12 MI 4.5

2. MI Workspace & Project Anatomy

Navigating the VS Code WSO2 extension, project files, and the core Synapse integration building blocks.

Tooling: The Modern VS Code Extension

WSO2 MI 4.5 development centers on the WSO2 Micro Integrator extension for Visual Studio Code. It provides a graphical low-code canvas alongside direct Synapse XML editing.

Integration Project File Structure

A typical MI project in VS Code contains:

my-integration-project/
├── pom.xml                               # Maven build configuration & dependencies
└── src/main/wso2mi/
    └── artifacts/
        ├── apis/                         # REST APIs exposed by MI
        ├── data-services/                # .dbs files (database queries)
        ├── endpoints/                    # Target backend definitions
        ├── sequences/                    # Reusable mediation pipelines
        └── local-entries/                # XML/JSON schemas or XSLT files

The Core Building Blocks

  • API (<api>): Exposes a REST HTTP listener on MI (port 8290/8253) with defined context and resources.
  • Sequence (<sequence>): An ordered pipeline of mediators that process a request or response. Common types include:
    • In-Sequence: Handles incoming request messages.
    • Out-Sequence: Handles response messages before returning to caller.
    • Fault-Sequence: Triggered whenever an exception or timeout occurs.
  • Endpoint (<endpoint>): Defines downstream target addresses, including timeouts, retries, and load-balancing.
⚠️ VS Code Testing: Build vs. Export

Build and Run runs the project on your local PC's embedded MI runtime for rapid testing. When deploying to the server (e.g. wso-mi-1), always use Export to generate the .car package!

Module 3 of 12 Data

3. Kind B: Data Services (.dbs)

Exposing SQL Server and PostgreSQL databases directly as clean REST APIs without writing backend server code.

What is a Data Service?

A Data Service (.dbs) is an XML specification in MI that maps relational databases directly to RESTful endpoints or SOAP services. MI manages connection pooling, SQL execution, parameter binding, and JSON serialization automatically.

1. Data Source Configuration

Configuring a connection to Microsoft SQL Server or PostgreSQL:

PhoneBook.dbs (Data Source)
<data name="PhoneBook" serviceGroup="" serviceNamespace="">
   <config id="PhoneBookParsDS">
      <property name="driverClassName">com.microsoft.sqlserver.jdbc.SQLServerDriver</property>
      <property name="url">jdbc:sqlserver://172.27.25.140:1433;databaseName=PhoneBookPars;encrypt=false;trustServerCertificate=true</property>
      <property name="username">mi_user</property>
      <property name="password">SecretPass123</property>
   </config>
</data>
🚨 JDBC 13 Default Encryption Trap

Microsoft JDBC driver version 13 enables encryption by default. If your lab SQL Server does not have a trusted TLS certificate, connection test will fail immediately unless you append:
encrypt=false;trustServerCertificate=true

2. Queries & Resource Mapping

You map a SQL query to an output structure, and then bind that query to a REST resource:

Query & Resource Definition
<!-- Define Query -->
<query id="GetPhonesQuery" useConfig="PhoneBookParsDS">
   <sql>SELECT ContactId, FullName, PhoneNumber FROM dbo.Contacts</sql>
   <result outputType="json">
      {
        "PhoneNumbers": {
          "Person": [
            {
              "Id": "$ContactId",
              "Name": "$FullName",
              "Phone": "$PhoneNumber"
            }
          ]
        }
      }
   </result>
</query>

<!-- Expose as REST Resource -->
<resource method="GET" path="phones">
   <call-query href="GetPhonesQuery" />
</resource>

The Automatic URL Rule for Data Services

Data services in MI do not have arbitrary base paths. MI exposes them according to this mandatory URL structure:

http://<mi-host>:8290/services/<ServiceName>.HTTPEndpoint/<ResourcePath>

# Example:
http://wso-mi-1:8290/services/phonebook.HTTPEndpoint/phones
Module 4 of 12 EIP

4. Mediators & Transformation (EIP)

Mastering the essential Synapse mediators to transform, filter, enrich, and route messages.

The Essential Mediators

In WSO2 MI, mediators are the verbs of your integration pipelines. Here are the 5 mediators you will use 90% of the time:

1. Property Mediator (Variables & Headers)

Used to read, set, or remove properties from the Synapse message context or HTTP transport headers.

<!-- Save query parameter 'customerId' into a Synapse variable -->
<property name="targetId" expression="$url:customerId" scope="default" />

<!-- Set an outgoing HTTP header -->
<property name="X-Source-System" value="PARS-MI" scope="transport" />

2. PayloadFactory Mediator (Constructing Payloads)

Builds a new JSON or XML payload using template placeholders and JSONPath/XPath arguments:

<payloadFactory media-type="json">
    <format>
        {
            "status": "PROCESSED",
            "reference": "$1",
            "account": {
                "id": "$2",
                "type": "SAVINGS"
            }
        }
    </format>
    <args>
        <arg evaluator="xml" expression="$ctx:refNumber"/>
        <arg evaluator="json" expression="$.customer.accountId"/>
    </args>
</payloadFactory>

3. Filter & Switch Mediators (Branching)

Conditional execution based on headers, query parameters, or payload content:

<filter source="get-property('transport', 'Accept')" regex=".*application/xml.*">
    <then>
        <property name="messageType" value="application/xml" scope="axis2"/>
    </then>
    <else>
        <property name="messageType" value="application/json" scope="axis2"/>
    </else>
</filter>

4. Call vs. Respond

  • <call>: Invokes an external endpoint synchronously and pauses sequence execution until the response returns, then continues to the next mediator.
  • <respond>: Halts mediation immediately and sends the current message payload back to the client.

5. Fault Sequence (Error Handling)

Catches backend timeouts or exceptions, returning friendly JSON error structures:

<faultSequence>
    <property name="HTTP_SC" value="502" scope="axis2"/>
    <payloadFactory media-type="json">
        <format>
            {"error": "Backend Service Unavailable", "detail": "$1"}
        </format>
        <args>
            <arg evaluator="xml" expression="$ctx:ERROR_MESSAGE"/>
        </args>
    </payloadFactory>
    <respond/>
</faultSequence>
Module 5 of 12 Packaging

5. Packaging & Deployment: The CAR Rule

Understanding Composite Applications, hot-deployment, and avoiding the FAT vs. Thin CAR dependency trap.

What is a Carbon Application (.car)?

WSO2 packages integrations into a .car (Composite Application) file. It is a ZIP file containing artifacts, XML metadata, and an artifacts.xml manifest.

🚨 The Golden Law: Never ZIP in Windows Explorer

Do not use Compress-Archive or right-click "Send to Compressed ZIP" and rename the extension to .car! MI will fail to extract the archive and throw Error while extracting. Always use the VS Code Export feature or Maven build.

The FAT CAR vs. Thin CAR Rule

When you create an integration that uses connectors (like mi-connector-http):

Thin CAR (Default)

The exported .car contains only your project XML. It assumes all connectors are already installed on the MI server. If the server does not have them, deployment fails with:

Some dependencies were not satisfied in cApp:PhoneBook_1.0.0

Result: The service is not deployed. Calls return 404 Not Found.

FAT CAR (Required Solution)

A FAT CAR bundles the connector ZIPs directly inside the .car package, making it 100% self-contained.

How to enable FAT CAR:

  1. In VS Code, open Project Overview → Build Details.
  2. Check Enable FAT CAR (or set <fat.car.enable>true</fat.car.enable> in pom.xml).
  3. Click Export again.

Deployment Lifecycle

To deploy on your server (e.g. wso-mi-1):

  1. Copy the .car file to:
    /opt/wso2/wso2mi-4.5.0/repository/deployment/server/carbonapps/
  2. Ensure the file is owned by the wso2 user:
    sudo chown wso2:wso2 PhoneBook_1.0.0.car
  3. Monitor the log:
    sudo tail -f /opt/wso2/wso2mi-4.5.0/repository/logs/wso2carbon.log
  4. Verify you see:
    Successfully Deployed Carbon Application : PhoneBook_1.0.0
Module 6 of 12 Catalog

6. The Bridge: Service Catalog

Connecting MI to APIM: How integration services register themselves automatically into Publisher.

Why Service Catalog?

Historically, connecting an ESB to an API Manager required manually exporting a WSDL or Swagger file and re-importing it into Publisher. WSO2's Service Catalog automates this completely.

How It Works

  1. When MI boots or a CAR is deployed, MI reads its deployed services and generates OpenAPI metadata.
  2. If Service Catalog is enabled in MI's deployment.toml, MI makes a secure HTTPS call to APIM Publisher (https://publisher.parspc.ir).
  3. APIM registers the service under Publisher → Services.
  4. The API developer simply clicks Create API from that listed service!

MI Configuration (deployment.toml)

MI conf/deployment.toml
[[service_catalog]]
apim_host = "https://publisher.parspc.ir"
enable = true
username = "admin"
password = "$secret{admin_password}"
⚠️ The PKIX Trust Rule

Because MI calls APIM over HTTPS, APIM's public TLS certificate (or CA) must be imported into MI's client-truststore.jks. If you forget this, MI will fail to register services with a PKIX path building failed: SunCertPathBuilderException.

7. APIM Publisher: Designing APIs

Creating, configuring resources, and applying governance policies in the Publisher portal.

Publisher Overview

The Publisher Portal (https://publisher.parspc.ir/publisher) is where API designers shape how the outside world interacts with your internal services.

Creating an API: Two Approaches

  • From Service Catalog (Kind B): Go to Services, find phonebook, and click Create API. Context and basic resources are pre-populated.
  • Design New REST API (Kind A): Click Create API → Design a New REST API. Provide:
    • Name: PhoneBook
    • Context: /phonebook (The public URL prefix)
    • Version: 1.0.0
    • Endpoint: The target backend address

Configuring Resources (Paths & Operations)

Under API Configurations → Resources, define what HTTP methods and paths clients can call:

MethodResource PathOperation Description
GET/phonesRetrieve list of all phone contacts
GET/phones/{id}Retrieve contact by specific ID
POST/phonesCreate a new contact

Attaching Policies (Mediation in APIM)

Under API Configurations → Policies, you can drag-and-drop runtime policies to request, response, or fault flows without modifying your backend code:

  • Header Manipulation: Add, remove, or modify HTTP headers.
  • CORS: Enable cross-origin resource sharing for web clients.
  • IP Filtering: Allow or deny traffic based on client IP.
  • Schema Validation: Validate client payloads against OpenAPI definitions before reaching the backend.
Module 8 of 12 Trap

8. The Endpoint Rule (Avoiding EPR 500)

The most common failure in WSO2 APIM: Why URLs get doubled and how to compose endpoint bases correctly.

The Anatomy of an Invocation URL

When a client calls an API through WSO2 APIM Gateway, three distinct URL fragments are involved:

FragmentWhere It Is ConfiguredExample Value
A. Public Gateway URLGateway domain + API Context + Versionhttps://api.parspc.ir/phonebook/1.0.0
B. Backend Endpoint BasePublisher → Endpointshttp://wso-mi-1:8290/services/phonebook.HTTPEndpoint
C. Resource PathPublisher → Resources/phones

The Golden Formula

What APIM actually calls on your backend is always:

Actual Backend Request = [B. Endpoint Base] + [C. Resource Path]
🚨 The Doubled Path Trap (EPR 500)

If you copy the full test URL from your browser or curl into Publisher's Endpoints box:

  • Endpoint Base (B) = http://wso-mi-1:8290/services/phonebook.HTTPEndpoint/phones
  • Resource Path (C) = /phones
  • Resulting Backend Request = .../phonebook.HTTPEndpoint/phones/phones ❌

MI does not have a resource named /phones/phones. It throws an Axis2 error: "The endpoint reference (EPR) for the Operation not found" and returns HTTP 500!

Try typing in the boxes below to see how APIM builds the final URL and detect doubled paths in real time:

9. Lifecycle & Deployment: Deploy ≠ Publish

The critical difference between deploying a revision to the Gateway and publishing an API to the Devportal.

The Golden Law: Deploy ≠ Publish

New API developers frequently get stuck because their API returns 404 Not Found even after clicking "Deploy". Remember:

Deployments (Gateway Runtime)

Creates a snapshot Revision of your configuration and deploys it to the Gateway nodes. The Gateway now knows the routes, but the API is not yet accessible to subscribers.

Lifecycle (Devportal Visibility & Governance)

Changes the API state from CREATED to PUBLISHED. This makes the API discoverable in the Developer Portal so applications can subscribe and generate tokens.

⚠️ You Must Do Both!

An API that is CREATED (even if deployed) will return Gateway 404 Not Found.
An API must be in the PUBLISHED state with an active revision deployed.

Subscription Business Plans Requirement

Before APIM allows you to publish an API, you must attach at least one Business Plan / Tier under Subscriptions (e.g., Unlimited, Gold, or Silver). If no tier is selected, the Publish button will remain disabled!

The API Lifecycle Stages

StageMeaningCan Gateway Invoke?
CREATEDDraft design in progress.No (Returns 404)
PROTOTYPEDMocked responses for early testing.Yes (Sandbox keys only)
PUBLISHEDLive production API. Visible in Devportal.Yes (Full access)
BLOCKEDTemporarily disabled for maintenance.No (Returns 503)
DEPRECATEDStill works, but warning consumers to migrate.Yes (Existing subscribers only)
RETIREDDecommissioned permanently.No (Returns 404)
Module 10 of 12 Devportal

10. Devportal: Subscriptions & Keys

How application developers discover APIs, manage applications, and generate OAuth2 Bearer tokens.

The Consumer Journey

The Developer Portal (https://devportal.parspc.ir/devportal) is the storefront for your APIs. Consumers follow four straightforward steps:

  1. Discover: Browse published APIs and inspect their documentation, schemas, and endpoints.
  2. Create an Application: Set up a logical container for your client project.
  3. Subscribe: Tie your Application to the desired API with a throttling tier (e.g. Unlimited).
  4. Generate Keys: Obtain OAuth2 credentials (Client ID & Secret) and Access Tokens.

Why Use "Applications"?

In WSO2, client credentials are never tied directly to individual user accounts. Instead, they are tied to Applications. This provides:

  • Decoupling: One application can subscribe to 10 different APIs using a single access token.
  • Key Separation: Independent keys for Production vs. Sandbox environments.
  • Traffic Throttling: Enforcing rate limits at the consumer application level.

Generating Keys & Tokens

Under your Application → Production Keys:

  1. Click Generate Keys. APIM assigns a Consumer Key and Consumer Secret.
  2. Click Generate Token. Choose expiration time and scopes.
  3. Copy the Bearer token:
    eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...

11. Invocation & Diagnostics (Status Codes)

Diagnose and resolve Gateway errors instantly using the status code triage matrix.

Invoking the Gateway with cURL

Always test your published API using the Gateway URL and your Bearer token:

Terminal (cURL)
# 1. Without Token (Expect 401 Unauthorized)
curl -vk https://api.parspc.ir/phonebook/1.0.0/phones

# 2. With Bearer Token (Expect 200 OK + JSON Payload)
curl -vk -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
     https://api.parspc.ir/phonebook/1.0.0/phones
